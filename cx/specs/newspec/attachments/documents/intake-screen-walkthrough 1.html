Authoring Workspace — one reusable shell, first instance: spec intake

Intake (confirmed) authors a spec to be implemented later — a spec/PRD registry, not a runnable-agent vibe-coder. So the design goal isn't one screen; it's a reusable "authoring workspace" shell that every SDLC surface renders through — spec intake first, the feature editor next, and a future permission-gated "do-the-whole-thing" intake — so users learn one layout and reuse it everywhere. This is the VS Code / Linear / Figma / Notion move: one shell, many contexts.

1The reusable shell (six zones)

Every authoring surface is the same skeleton; only the content of each zone changes. Learn it once, and the feature editor + advanced intake are instantly familiar.

A
Context bar
project · artifact switcher (▾, not a list) · status/version · primary action (Accept / Advance / Ship — permission-gated)
B
Stepper — the lifecycle
the domain's stages, current highlighted (spec: Vibe→Compile→Review→Accept · feature: Planning→…→Done · advanced: the full SDLC)
F
Copilot chat — one thread
left rail (Canvas / Artifacts). The first message generates (vibe→compile, or generate-plan), the rest refine.
D
Artifact pane — the middle
the document being authored (markdown), with select-to-comment (margin threads) and a compact section switcher (zone C, folded in). The one thing you're focused on.
E
Inspector rail (tabbed)
Checks (validation / readiness / review) · Comments (the doc's threads, listed) · ▦ slot (future: Preview / Runs)
Canonical arrangement = Canvas / Artifacts: chat on the left, the editable document in the center, an inspector rail on the right — exactly Claude Artifacts and ChatGPT Canvas (chat beside a live editable artifact). The reusable-shell idea still holds — VS Code, Linear, Figma, Notion all keep one skeleton across contexts — we just fix the chat as a left rail rather than a bottom dock. Consistency is the feature. (Zone C — doc sections — folds into the artifact as a compact switcher, since the left column is now the chat.)
In build-model terms: the shell is a reusable base model+view (an AbstractAuthoringWorkspaceModel, in the spirit of the existing AbstractDocumentEditorModel / AbstractBuildConfigTabModel bases). Concrete screens configure it — the stepper stages, the artifact source, the inspector tabs, the primary action, and what the chat's first message does — and inherit the rest.

Advanced intake (future, permission-gated) — same shell, fuller config

Vibe› Spec / accept› Create feature› Plan · Tasks · Implement› Merge› Deploy
If the caller has the permissions to do the whole thing, the Stepper (B) renders the full SDLC, the primary action (A) becomes "Take it live" (each step gated by permission), and the ▦ slot (E) can host a preview/runs pane. A restricted user sees the same shell truncated to Vibe → Accept. slot = backend not built yet (merge/CI/deploy are the SDLC-tail gaps) — the shell is ready; the capability is phased.
vs. other products: permission-scoped depth is Linear/Jira workflow + GitHub Actions gates — the same view shows more or fewer steps by role. And a single "keep going" primary action that walks a pipeline is Vercel/Netlify deploy / Copilot Workspace.

6Design decisions, benchmarked

DecisionWhy (vs. products)
One reusable shell for every authoring screenVS Code / Linear / Figma / Notion — one skeleton, many contexts. Users learn once; the feature + advanced screens come "for free" and feel familiar.
Focused artifact + inspector rail + one chatChatGPT Canvas / Claude Artifacts / v0 (chat + live artifact) and Figma/VS Code (inspector rail). The vibe is the chat's first message — no separate box.
Inline anchored commentsGoogle Docs / Notion / GitHub review — select → thread; LLM review shares the same threads.
"Checks" tab instead of a run sandboxA spec isn't executed at intake (implemented later), so validation/readiness (Checks) maps; a live preview belongs to the ▦ slot / the feature-run screen — the AgenticFactory preview was a vibe-coder feature.
Stepper + primary action are permission-scopedLinear/Jira workflows + Actions gates — the same view shows more steps to those allowed to do more.

Backend as built (spec instance): SpecEditorService (createSpecEditor / compile / save / read / readVersion / diff / review / assess / chat) + SpecWorkflow (accept) + SpecRegistrySheet (live registry). The reusable shell + these bindings are the UI work; the advanced-intake tail (merge/CI/deploy) is deferred backend.
