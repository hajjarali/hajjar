The intake screen — what the middle pane actually is

Resolving the confusion: is the center the markdown document, the chat, both, or tabs? The answer is the Artifact + Conversation pattern (Claude Artifacts / ChatGPT Canvas / Google Docs + Gemini): the center is the editable spec document, the chat is a separate coordinated panel, and they share one source of truth. Every zone below names the real element that backs it.

1The one principle that removes the confusion

A conversation and an artifact are two different things and must be two different surfaces. The chat is where you talk about the spec; the document is the spec itself. They are kept side by side and both write the same underlying SpecIR (a MarkdownDocumentData). This is precisely how mature tools do it:

4Your three questions, answered

“Is the middle our markdown view, or the chatElement?”

DOC The markdown editor.

The middle is IMarkdownEditorElement (editable, with margin comments) — not the read-only RichText display, and not the chat. The chat is a separate panel.

“Should the chatElement display a MarkdownEditorElement inside it?”

NO Don’t nest them.

Nesting the doc in the chat conflates conversation with artifact and breaks direct editing + comments. Keep them side by side, sharing the SpecIR.

“Should the middle be 2 tabs?”

NOT chat/doc One editor.

The center is one editor. Tabs only make sense later as Document / Versions-diff (same spec, another view via readVersion/diff) — never doc-vs-chat. Chat stays always-visible.

What actually felt missing is not an element — it is the coordination. When the chat edits the spec, the center editor must re-read and reload; and before a spec exists, the chat’s first message (the vibe → compile) is what fills the empty editor. Both are model wiring, shown next.

5The data flow — how the two panels stay in sync

Both the direct-edit path and the chat path write the same SpecIR; the difference is only who initiates. The one piece to add for intake (the feature editor doesn’t need it because it has no chat) is “after a chat turn, re-read the doc into the editor.”

  Note over Doc: center re-renders with the new content

  Doc->>M: direct edit (onContentChange) -- marks dirty
  M->>SE: save(ir)  -- autosave DRAFT
  M->>SE: validate(ir) + review(ir)
  SE-->>M: findings + anchored comments
  M->>Doc: merge review comments into editor.comments
Direct edits flow editor.onContentChange → the model (dirty → save). Chat edits flow through the server then back via read → editor.content.set. Review comments (Gap 2) land as editor.comments — margin threads. Validate findings (Gap 3) feed the right rail.

6The states — cold start to accepted version

The center pane has states; the chat is the entry point that moves it out of empty.

stateDiagram-v2
  [*] --> Empty: open intake (no spec yet)
  Empty --> Drafting: chat vibe → compile → first doc fills the editor
  Drafting --> Drafting: edit directly / chat refine / review / validate (autosave DRAFT)
  Drafting --> Accepted: Accept vN (validate passes → freeze commit)
  Accepted --> Drafting: edit again (amend → new DRAFT)
  Accepted --> Viewing: open an older version (readOnly)
  Viewing --> Drafting: back to the live draft
Empty state = the editor is blank and the chat says “describe what you want.” That is the vibe-coder cold start — no separate screen, just the same three panels with an empty center. Viewing a version flips the editor readOnly (the property already exists).

7What we reuse vs. what is new

REUSE The editor stack

MarkdownEditorModel + IMarkdownEditorElement (content, comments, readOnly, change hooks) and the AbstractDocumentEditorModel pattern (seed / dirty / commit) — already in build-model for the feature spec/plan/tasks tabs.

REUSE The chat element

IChatElement + a chat model — the same element the copilot uses — pointed at SpecEditor.chat.

NEW The coordination + shell

The intake model that (a) fills the editor from compile on cold start, (b) re-reads the doc after each chat turn, (c) feeds the checks rail from validate/review, (d) the 3-pane shell = the reusable Authoring Workspace. No new element type.

Bottom line: the middle is one thing — the editable spec document (IMarkdownEditorElement). The chat is a peer panel, never a container for it, never a tab against it. Everything the pane needs already exists as an element; intake is the model that coordinates the three panels over the finished SpecEditor backend.
